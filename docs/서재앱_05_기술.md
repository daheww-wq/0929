**서재앱 05 기술** (초안)

이 문서가 답하는 질문: 01~04에서 정한 것이 뒤에서 어떻게 돌아가나
현재 기준 문서. 결정이 바뀌면 이 자리에서 고친다. 바뀐 이력은 `서재앱_00_허브.md` 결정 로그에 남긴다.
버전 구분은 03, 화면은 04, 규칙과 수치는 02를 따른다. 이 문서는 "어떻게 만드나"만 다룬다.
숫자로 적힌 판정 기준(비교, 로그인 판별, 잘림 판정)은 모두 초기값이다. 읽기 품질 스파이크(7절)에서 실측해 바꾼다.
말의 주체: "나"는 서재앱 사용자(다혜), "사서"는 앱 안의 LLM.
용어: "들어오는 글"은 칸마다 이 칸에 들어오는 것과 다른 칸으로 가는 것을 적은 기준이다 (02 1절).

**1. 전체 구조**

```
[크롬 확장]                                  [우리 서버]                          [저장소]
 새 탭·뷰어·설정 화면 (Vite + React)  ──API──>  FastAPI (Railway)                 관리형 Postgres
 백그라운드: 북마크 감지, 장서 점검,           작업 큐 (procrastinate)            ├ 서비스 저장소: 메타, 칸, 기록
            대기열, 로그인 토큰                 수집 워커: 받아오기·본문 추출       └ 검색 색인
 페이지 위: 탭 본문 뜨기, S30 알림             분류·요약 워커 ──> LLM API         Cloudflare R2
                                                                                  └ 원문 저장소: 본문, 이미지, PDF
```

- 확장은 화면과 크롬 안에서만 할 수 있는 일(북마크 읽기, 탭 본문 뜨기)을 맡는다
- 서버는 수집, 분류, 요약, 저장, 검색을 맡는다. 확장이 꺼져 있어도 서버 일은 계속된다
- 원문 저장소와 서비스 저장소는 처음부터 나눈다 (9절)

**2. 스택**

| 부분 | 선택 | 이유 |
|---|---|---|
| 화면 | Vite + React, 확장에 번들 | 확장은 외부 코드를 불러올 수 없어서 전부 묶어서 넣음. 3D 라이브러리와 폰트도 파일로 포함 |
| API·워커 | Python + FastAPI, Railway | 본문 추출 도구가 파이썬에 많음 |
| 본문 추출 (서버) | trafilatura | 기사 본문 추출 품질이 좋은 편 |
| 본문 추출 (확장) | Readability.js | 파이어폭스 읽기 모드에 쓰이는 방식. 탭의 HTML에서 본문만 골라냄 |
| 렌더링 | Playwright (필요할 때만) | 자바스크립트로만 그려지는 페이지용. 무거워서 기본 경로에서는 쓰지 않음 |
| PDF | pdfplumber | 텍스트 추출. 2단 조판은 약함 (7절) |
| DB | 관리형 Postgres (Supabase 등) | 데이터와 작업 큐, 검색을 한곳에서 |
| 작업 큐 | procrastinate | 파이썬, Postgres만으로 동작, 재시도·예약 포함. pg-boss는 Node 라이브러리라 제외 |
| 파일 | Cloudflare R2 | 원문 저장소. 비공개 버킷 |
| 로그인 | 구글 계정 (크롬 로그인 이용) | 5절 |
| LLM | 작은 모델 위주, 판단이 어려운 곳만 큰 모델 | 12절 |

비용: 월 1만 원 안쪽을 목표로 한다. 혼자 쓸 때는 웹스토어 등록 없이 개발자 모드로 설치한다. 등록할 때는 권한마다 쓰는 이유를 설명해야 한다 (3절).

지킬 것: 원문 저장소는 반드시 비공개. 공개 저장소·공개 버킷에 올리지 않는다 (사적 이용 범위 유지).

**3. 확장의 구성과 권한**

확장 파일 한 세트
- 설정 파일(manifest): 새 탭 바꾸기, 권한 목록
- 새 탭 페이지: S02를 비롯한 확장 안 화면
- 백그라운드 스크립트: 북마크 감지, 장서 점검, 대기열, 로그인 토큰 관리
- 페이지 스크립트: 원문 페이지 위에서 탭 본문 뜨기와 S30 알림

| 권한 | 쓰는 곳 | 비고 |
|---|---|---|
| 새 탭 바꾸기 | S02 | 켜고 끌 수 없음. 원래 새 탭으로 가려면 확장을 끔 (앱 정보에 안내) |
| 북마크 읽기·쓰기 | 자동 담기, 가져오기, 장서 점검, "서재" 폴더 옵션 | 쓰기는 "서재" 폴더 옵션을 켤 때만 |
| 모든 사이트 읽기 | 북마크한 탭의 본문 뜨기, S30 알림, 다시 담기 | 가장 민감한 권한. 결정 필요 (16절) |
| 저장소 | 로그인 토큰, 못 보낸 북마크 대기열 | 사본 책장은 두지 않음 (03 F1) |
| 구글 계정 | 로그인 | 5절 |
| 다운로드 | 내보내기 zip 받기 | |
| 알림 | 저녁 큐레이션 | 다음 버전에 요청 |

탭 본문을 뜨는 순간: 크롬은 북마크가 생기면 확장에 주소를 알려준다. 이때 백그라운드가 담지 않는 사이트인지 먼저 확인하고, 통과하면 그 주소가 열린 탭에 페이지 스크립트를 넣어 Readability로 본문을 뽑는다. 뽑은 본문은 확장 안에만 두고, 서버 결과와 비교가 끝난 뒤에 보낸다 (03 B1-1, B1-2).

**4. 수집 파이프라인**

단계 (03 B1-1 ~ B1-3과 같은 순서)

| 단계 | 어디서 | 하는 일 | 실패하면 |
|---|---|---|---|
| 거르기 | 확장 | 자동 담기 폴더, 서재가 만든 북마크, 담지 않는 사이트, 로그인 상태, 중복 주소 | 담지 않음 또는 대기열 |
| 탭 본문 뜨기 | 확장 | Readability로 제목·본문·이미지 주소 추출 | 탭이 없으면 건너뜀 (폰 북마크, 가져오기, 장서 점검) |
| 서버 수집 | 수집 워커 | 주소로 HTML 받기 → trafilatura. arXiv는 HTML 버전 우선. PDF는 pdfplumber | 3회 재시도(간격을 늘려가며), 그래도 안 되면 Playwright 렌더링, 그래도 안 되면 C등급 |
| 비교 | 수집 워커 | 탭 본문과 서버 결과 중 나은 쪽 고르기 (4-1) | |
| 로그인 판별 | 수집 워커 | 로그인해야 보이는 페이지인지 (4-2) | 판별되면 S30으로 물어봄 |
| 잘림 판정 | 수집 워커 | 탭 본문이 잘렸을 수 있는지 (4-3) | "일부만 담겼을 수 있어요" 표시 |
| 메타데이터 | 수집 워커 | 제목, 저자, 날짜, 출처, 분량, DOI·arXiv ID(버전 포함), 캡처 날짜 | 비어 있으면 탭 제목·주소로 채움 |
| 분류 | 분류 워커 | 3회 분류 → 칸, 참조 카드, 임시서가 (02 2·3절) | LLM 실패 시 "정리 중"으로 임시서가, 재시도 (03 F1) |
| 요약 | 분류 워커 | 초록 카드용 요약과 요약 문장별 근거 (12절) | 실패 시 "요약 만드는 중" 유지, 재시도 |
| 저장 | 서버 | 원문 저장소와 서비스 저장소에 나눠 저장, 신호 로그 | |

동시에 처리하는 양: 가져오기와 장서 점검은 두세 개씩 천천히. 같은 사이트에 한꺼번에 요청을 보내지 않는다.

**4-1. 나은 쪽 고르기 (초기값)**
- 둘 중 하나만 있으면 그것
- 둘 다 있으면: 깨진 글자 비율이 2%를 넘는 쪽은 제외. 남은 둘의 본문 길이 차이가 10% 이내면 서버 쪽(원본 HTML에서 뽑아 깨끗한 경우가 많음). 10% 넘게 차이 나면 긴 쪽
- 고른 이유를 기록한다 ("탭 본문이 42% 길어서"). 스파이크와 사서 기록에서 쓴다

**4-2. 로그인 판별 (초기값, 코드로 판단)**

다음 중 하나라도 맞으면 로그인해야 보이는 페이지로 본다.
- 서버가 받은 응답이 401 / 403이거나, 로그인 주소로 넘어감
- 서버가 받은 페이지에 비밀번호 입력칸이 있고 본문이 짧음
- 서버 본문 길이가 탭 본문의 30%보다 짧음
- 알려진 페이월 표시가 있음 (구독 안내 덮개 등)

LLM에게 "로그인 페이지 같아?"라고 묻지 않는다. 매번 같은 결과가 나와야 하는 판단이라 코드로 한다.

**4-3. 잘림 판정 (초기값)**

탭 본문만 있을 때 다음 중 하나라도 맞으면 "일부만 담겼을 수 있어요".
- 페이지에 "더보기", "Read more", "계속 읽기" 같은 펼치기 버튼이 남아 있음
- 마지막 문단이 문장 중간에서 끊김
- 페이월 덮개가 있음
- 본문이 같은 사이트의 다른 책들보다 눈에 띄게 짧음 (책이 쌓인 뒤)

**4-4. 같은 책 판단 (중복 합치기)**
- 주소를 정리해서 비교한다: 추적용 꼬리(utm 등) 제거, 끝의 `/` 통일, http와 https 같게 봄
- 논문은 DOI 또는 arXiv ID로 비교한다
- 결정 필요: arXiv의 v1과 v2는 같은 책의 다른 판으로 볼지, 다른 책으로 볼지 (16절)

**4-5. PC가 두 대일 때**
- 같은 구글 계정이면 서재는 하나. 두 확장이 같은 북마크를 보내도 4-4로 한 권이 된다
- 북마크 알림에는 크롬 북마크 ID가 같이 오므로, 같은 ID는 한 번만 처리한다
- 북마크한 PC에만 탭 본문이 있다. 서버 결과가 먼저 저장된 뒤 탭 본문이 늦게 오면, 4-1로 다시 비교해서 나으면 교체한다

**4-6. 출처별 경로 사다리**

| 출처 | 1순위 | 2순위 | 3순위 | 마지막 |
|---|---|---|---|---|
| 기사 | 서버가 HTML을 받아 본문 추출 | 북마크 순간의 탭 본문 (비교해서 나은 쪽) | 서버 렌더링 후 추출 | 링크 + 아카이브 주소 (C등급) |
| 로그인·유료 기사 | 탭 본문 (물어보고 담음) | 원문 페이지를 다시 열어 다시 담기 | | 링크 + 메모 (C등급) |
| arXiv 논문 | arXiv HTML 버전 | ar5iv | PDF 텍스트 추출 | 원문 PDF 뷰어 (B등급) |
| 오픈액세스 논문 | 출판사 HTML | 학술 PDF 구조 분석 (GROBID 등) | PDF 텍스트 추출 | 원문 PDF 뷰어 (B등급) |

**5. 로그인과 계정**

- 확장이 크롬의 구글 계정으로 토큰을 받는다. 처음 한 번 승인하면 그 뒤로는 자동
- 서버는 그 토큰이 진짜인지 구글에 확인하고, 우리 서비스용 토큰을 내준다. 확장은 이걸 저장소에 둔다
- 계정은 구글 계정 하나에 서재 하나. 다른 계정으로 로그인하면 그 계정의 서재가 열린다
- 준비할 것: 구글 클라우드에 로그인 설정(OAuth 클라이언트) 하나. 개발자 모드에서는 확장 ID가 바뀔 수 있어서, 설정 파일에 고정 키를 넣어 ID를 고정한다
- 토큰이 만료되면 크롬 계정으로 조용히 다시 받는다. 실패하면 새 탭에 "다시 로그인해 주세요" (03 A2)
- 로그아웃: 확장의 토큰과 대기열을 지운다. 서버의 서재는 그대로 (03 A3)
- 계정 삭제: 원문 저장소, 서비스 저장소, 검색 색인, 신호 로그를 지운다. 백업의 사본은 보관 기간(30일)이 지나면 사라진다 (03 A4, 흐름만 정의)

**6. 장서 점검과 대기열**

장서 점검 (03 B3)
- 언제: 크롬을 켤 때, 다시 로그인할 때, 다시 설치했을 때
- 어떻게: 크롬 북마크 목록 전체(주소, 폴더, 추가일, 북마크 ID)를 읽어, 서버가 "이미 본 목록"(담은 것 + 뺀 것 + 제외된 것)과 비교한다. 설치 이후 생겼는데 본 적 없는 것만 고른다
- 10개 이하면 조용히 서버 경로로 담고, 넘으면 사서가 묻는다
- 서버에는 있는데 크롬에서 사라진 북마크는 보존 서고로 (03 B5)
- 목록끼리 비교만 하므로 가볍다. 수집은 고른 것만

대기열
- 로그인이 풀렸거나 서버에 연결하지 못할 때 한 북마크는 확장 저장소에 주소와 탭 본문을 둔다. 서버로는 보내지 않는다
- 연결되거나 로그인하면 차례로 보낸다. 로그인이 풀린 동안의 것은 담을지 먼저 묻는다 (03 A2)
- 대기열에 쌓인 탭 본문은 7일이 지나면 지운다 (로그인 페이지 알림을 놓친 경우와 같은 기한)

**7. 읽기 기준선과 읽기 품질 스파이크**

읽기는 차별점이 되지 못해도 없으면 나머지가 성립하지 않는 바닥이다. 하이라이트와 메모는 전부 본문 위에서 일어나므로, 본문이 깨지면 해석도 성장도 재료가 생기지 않는다. 경쟁하지는 않되 기준선은 숫자로 관리한다.

읽기 등급

| 등급 | 상태 | 할 수 있는 것 |
|---|---|---|
| A | 본문을 깨끗하게 뽑음 | 텍스트 모드로 읽기, 요약, (다음 버전) 하이라이트·메모·용어 설명 |
| B | 본문은 못 뽑고 화면은 남김 (스냅샷·PDF) | 원문 모드로 읽기. 텍스트 하이라이트는 제한 |
| C | 원문을 못 가져옴 | 링크 + 메타데이터 + 아카이브 주소 (+ 다음 버전에 책 전체 메모) |

- 어떤 등급이든 책은 서재에 꽂히고 칸도 정해진다. 메타데이터와 아카이브 주소는 항상 남는다
- "일부만 담김"은 등급과 따로 붙는 표시다 (4-3)
- 원문 비우기를 하면 C등급이 된다

읽기 모드 두 개
- 텍스트 모드(기본): 뽑아낸 본문. 조판은 사라져도 하이라이트·메모가 된다
- 원문 모드: 원본 그대로. 표·수식 확인용. 원문 페이지 위에서 직접 하이라이트하는 것(다음 버전)과는 다르다

현실적인 기대
- 일반 기사: 잘 되지만 본문 외 요소(관련 기사, 구독 배너, 사진 설명, 기자 소개, 중간 광고)가 섞인다
- arXiv 논문: HTML이 있으면 좋다. 오래된 논문·복잡한 수식은 변환 실패도 있다
- 그 외 논문 PDF: 어렵다. 2단 조판에서 문장 순서가 섞이고 각주·머리말이 본문에 끼어든다
- 로그인·유료 기사: 탭 본문 경로로 가능. 잘림이 생길 수 있다

관리할 지표 (사서 데스크와 운영용)
- 깨끗하게 열린 비율 (매체별, 유형별, 경로별)
- 경로별로 이긴 비율 (4-1에서 서버 / 탭 본문 / 렌더링 중 어느 쪽이 골라졌나)
- 로그인·유료라서 서버가 못 가져온 비율. 공개 전 약관·법 재판단의 근거 (03 6절)
- 일부만 담김 비율, 다시 담기 비율
- 텍스트 모드에서 원문 모드로 넘어간 비율
- 요약 근거를 찾지 못한 비율 (12절)

읽기 품질 스파이크 (목표치를 먼저 정하지 않고 측정부터)
1. 평소 담을 법한 링크 35개: 기사 20(한국 매체 포함), arXiv 5, 그 외 논문 PDF 5, 로그인해야 보이는 페이지 5(잡코리아 공고 등)
2. 경로별로 돌려보기: 서버 단순 수집 / 서버 렌더링 후 수집 / 확장의 탭 본문
3. 채점: 본문 누락 / 문장 순서 / 본문 외 혼입(몇 개, 어느 위치) / 깨진 글자 / 그림·표 보존 / 읽을 만한가(그대로 읽기·거슬리지만 읽힘·못 읽음)
4. 판정 기준도 같이 재기: 4-1 비교, 4-2 로그인 판별, 4-3 잘림 판정이 사람 판단과 맞는지
5. 결과로 기준선, 초기값, 첫 버전 대상 범위 확정 (예: "첫 버전은 기사와 arXiv만")

- 본문 외 혼입은 위치를 함께 본다. 앞뒤에만 붙으면 규칙으로 잘라내기 쉽고, 중간에 끼어들면 어렵다
- 핵심 질문: 무거운 서버 렌더링이 정말 필요한지, 탭 본문으로 충분한지

**8. 이미지 처리**

| 대상 | 방식 |
|---|---|
| 기사 사진 | 담을 때 받아 저장(지연 로딩 주소 처리, 가로 1600px·가벼운 형식으로 변환). 캡션 함께 저장. 로고·아이콘·투명 픽셀은 크기·비율로 걸러냄 |
| arXiv HTML 논문 | 그림 파일이 따로 있어 그대로 가져옴 |
| 그 외 논문 PDF | 텍스트 모드에는 "그림 1이 여기 있었어요" 자리표시, 누르면 원문 모드의 해당 페이지로. 페이지 통째 잘라 보여주는 건 다음 버전 |

그림 설명 (다음 버전 2순위)
- 순서: 원문 캡션이 있으면 그것 → 없으면 LLM이 봄 → LLM이 쓴 설명에는 "사서가 본 그림" 표시
- 담을 때 전부 만들지 않고 "이게 뭐야?"를 누를 때만 만들고 저장. 비용이 크게 줄어든다
- 그림 종류별 난이도: 사진은 무난, 다이어그램은 대체로 가능, 그래프·표는 축과 수치 오독 위험
- 프롬프트에서 수치를 단정하지 않게 하고 원본 보기 버튼을 항상 함께 둔다. 논문에서 그림은 결론의 근거일 때가 많아 설명만 믿으면 해가 된다
- 신호: 설명을 보고 원본을 열어봤는지, 설명을 고쳤는지 → 어떤 종류의 그림에서 사서가 약한지 드러남

공유할 때는 이미지를 빼고 내 메모와 링크만 보낸다 (그다음 버전).

**9. 저장 구조 (상업화 대비)**

두 저장소를 논리적으로 분리한다. 지금은 같은 서버에 있어도 경로와 테이블을 따로 둔다.

| 원문 저장소 (소유자: 사용자) | 서비스 저장소 (소유자: 서비스) |
|---|---|
| 본문 텍스트, 이미지, PDF 스냅샷 | 메타데이터, 원본 링크, 아카이브 주소 |
| | 내 메모·하이라이트, 책 전체 메모 |
| | 그림 설명, 용어 설명, 요약 |
| | 분류 결과, 칸 구조, 들어오는 글, 신호 로그 |

지킬 네 가지
1. 원문 저장소와 서비스 저장소를 코드와 데이터 모델에서 분리
2. 화면은 원문이 없어도 성립하게 만든다 (본문이 없으면 요약·메모·설명·링크만으로도 책이 열림. C등급 화면이 곧 이 모습)
3. 이미지는 자리표시 + 설명을 기본으로, 원본은 "원본 보기" 한 단계 안에
4. 서비스가 새로 만든 텍스트(요약, 그림 설명, 용어 설명)는 서비스 저장소에. 원문 복제가 아니라 새 표현이라 상업화해도 남는 자산

- 이미지를 숨기는 것 자체는 저작권 판단을 바꾸지 못한다. 기준은 누가 저장하고 돈을 받느냐다. 지금은 혼자 쓰므로 사적 이용 범위 안이고, 공개·유료화 시점에 원문 저장소만 사용자 쪽으로 옮긴다
- 본문·이미지를 불러오는 코드를 한 군데로 모아둔다. 나중에 "사용자 저장소에서 가져오기"를 추가해도 화면은 손대지 않아도 되게
- 확장으로 바뀌면서, 상업화 시 "확장이 뜬 본문을 사용자 저장소에 직접 넣고 서버는 메타만 받는" 구조가 가능해졌다. 첫 버전에서는 서버 저장 그대로 두고 분리만 지킨다

원문 비우기 (03 C9)
- 지우는 것: 원문 저장소의 본문 텍스트와 이미지·PDF, 서비스 저장소의 요약(원문으로 만든 것이라), 검색 색인의 본문
- 남기는 것: 제목, 링크, 칸, 이동 기록, 메모
- 백업의 사본은 보관 기간 30일이 지나면 사라진다. 화면에 "백업에서는 30일 뒤 사라져요"로 알린다
- 분류와 요약 때 본문이 LLM API로 넘어간 적이 있다. API 회사의 로그 보관은 우리가 지울 수 없으므로 수집 범위 안내에 적는다

**11. 검색**

- 제목·메타데이터·요약·본문 전체에서 찾는다. 보존 서고 책도 나온다
- Postgres 안에서 한다. 한국어는 띄어쓰기 단위 검색이 약해서, MVP는 글자 조각 일치(pg_trgm)로 부분 검색을 받치고 제목에 가중치를 둔다
- 결과마다 어디서 찾았는지(제목 / 요약 / 본문 문장)를 돌려준다. 본문에서 찾았으면 그 문장 위치로 뷰어를 연다
- 못 찾은 검색어는 기록한다 (수서의 재료)
- 한국어 검색 품질(형태소 분석 등)과 임베딩 기반 의미 검색은 쓰면서 고도화 (03 D2)

**12. LLM 호출 지점**

| 지점 | 하는 일 | 몇 번 | 모델 | 코드가 확인하는 것 |
|---|---|---|---|---|
| 분류 | 책 하나를 칸에 배정 | 책마다 3회 | 작은 모델 | 칸 이름이 실제 칸 목록에 있는지, 3회 일치 여부 |
| 요약 | 초록 카드 요약 + 문장별 근거 인용 | 책마다 1회 | 작은 모델 | 근거 인용이 원문에 실제로 있는지 |
| 칸 초안 | 가져온 책들을 보고 칸 제안 (가져오기 뒤) | 한 번 | 큰 모델 | 칸 수(3~7), 모든 책이 어느 칸엔 들어가는지 |
| 규칙 후보 | 옮긴 책 3권으로 들어오는 글 수정안 | 질문마다 1회 | 큰 모델 | 형식, 건드리는 칸이 두 개뿐인지, 기존 문장과 겹치지 않는지 |
| 영향 미리보기 | 새 들어오는 글로 다시 분류 | 질문마다 최대 20회 | 작은 모델 | |
| 정답지 회귀 | 새 들어오는 글로 정답지 다시 분류 | 질문마다 20회 (버전마다 저장해 재사용) | 작은 모델 | 정답과 일치율 |
| 사서의 말 | 보고·질문 문장 다듬기 | 필요할 때 | 작은 모델 | 문장 속 사실값(날짜, 권수, 칸 이름)이 기록과 같은지 |

- 분류 3회는 같은 질문을 세 번 던져 흔들림을 보는 것이라, 답이 조금씩 달라질 수 있게 설정한다. 흔들림이 곧 경계 책 신호다 (02 3절)
- 요약 근거 확인: 요약을 만들 때 문장마다 "원문의 어느 문장을 보고 썼는지"를 같이 받는다. 코드가 그 문장이 원문에 실제로 있는지 찾아보고, 없으면 "근거를 찾지 못했어요"로 표시하고 기록한다 (03 D3). 자동 환각 검사(다음 버전)의 가벼운 전 단계
- 사서 기록은 사실을 로그에서 코드로 가져오고, LLM은 문장만 다듬는다. "왜 그랬는지"를 지어내지 않게
- 프롬프트와 들어오는 글은 버전으로 관리한다. 분류 기록에 어느 버전으로 분류했는지 남긴다
- 비용: 규칙 질문 한 번에 최대 41회, 하루 질문 상한 2개라 하루 82회가 최대. 가져오기 200권이면 분류 600회 + 요약 200회. 작은 모델이면 크지 않지만 스파이크 때 실측한다
- 모델 이름과 가격은 자주 바뀌므로 문서에 박지 않고, 쓸 때 확인한다

**13. 백업과 장애**

- DB는 매일 자동으로 비공개 저장소에 복사하고, 30일 보관한다. 원문 파일(R2)은 버전 보관을 켜서 30일 안에는 되살릴 수 있게 한다
- 복원은 MVP에서 화면 기능이 아니라 운영 작업이다 (04 S12)
- 서버가 응답하지 않으면 확장은 사본을 보여주지 않고 "서재에 연결하지 못했어요"만 띄운다. 그동안의 북마크는 대기열에 둔다 (03 F1)
- 수집 실패 목록(S13)은 운영 로그를 겸한다. Hermes가 멈춘 원인이 결정론적 실패(스케줄러·권한·API 제한)였고, 이런 실패는 로그를 봐야 잡힌다

**14. 내보내기 (03 E5)**

파일 구성

```
서재/
  LLM 평가/                          ← 칸이 폴더
    Who Validates the Validators.md  ← 책 한 권이 파일 하나
  에이전트/
  _임시서가/
  _보존서고/
  _원문/                              ← PDF, 이미지 같은 원본 파일
```

- 파일 안쪽: 맨 위 정보(frontmatter: title, authors, source, arxiv, published, captured, type, shelf, archive) + 요약 / 내 메모 / 하이라이트(인용 + 본문 위치) / 용어 / 원문(기본 포함)
- 파일 이름 규칙: 파일 이름에 못 쓰는 글자(`/ \ : * ? " < > |`)는 공백으로 바꾸고, 80자에서 자른다. 같은 칸에 같은 이름이 있으면 뒤에 `(2)`를 붙인다
- 이미지는 `_원문/` 아래 책별 폴더에 두고, 본문에서는 상대 경로로 가리킨다
- 결정 필요: 참조 카드와 관련 칸을 옵시디언 링크(`[[에이전트]]`)로 넣을지 (16절)
- 서버에서 zip을 만들고, 다 되면 사서가 알린다. 받기는 확장의 다운로드 권한으로

옵시디언과 연결하는 방법

| 방식 | 내용 | 시점 |
|---|---|---|
| 내보내기 | zip으로 받아 볼트에 넣기 | MVP |
| 깃허브 비공개 레포 동기화 | 서버가 레포에 올리고 옵시디언 Git 플러그인이 볼트로 당겨옴 | 다음 버전. Phase 앱 구상과 같은 길 |
| 폴더 동기화 | 드롭박스·아이클라우드 | 다음 버전 |

양방향은 나중으로. 처음에는 서재앱 → 볼트 한 방향만.

**15. 보안과 개인정보**

- 원문 저장소는 비공개 버킷. 화면에서 원문 파일을 보여줄 때는 짧게 유효한 주소를 그때그때 만든다
- 권한은 필요한 것만 요청한다. 알림 권한은 쓰는 기능이 붙을 때
- 수집 범위 안내(온보딩, 앱 정보)에 적을 것: 모으는 것, 모으지 않는 것, 로그인 페이지는 물어보고 담음, 크롬 북마크는 읽기만 함, 분류·요약 때 본문이 LLM API로 전송됨
- 담지 않는 사이트 확인은 탭 본문을 뜨기 전에 한다. 순서가 바뀌면 이미 뜬 뒤라 소용없다
- 로그인해야 보이는 페이지의 탭 본문은 대답 전까지 서버로 보내지 않는다
- 공개·유료화 전에는 저작권·약관 전문가 확인 (근거는 99)

**16. 결정 필요와 리스크**

결정 필요
- **모든 사이트 읽기 권한**: 북마크한 탭의 본문을 뜨려면 필요하다. 가장 민감한 권한이라 웹스토어 심사와 사용자 신뢰에 걸린다. 방법 둘: 설치할 때 바로 받기 / 온보딩에서 이유를 설명하고 따로 요청하기(선택 권한). 추천: 온보딩에서 따로 요청. 거절하면 서버 경로만 쓰고 로그인 페이지는 C등급
- **arXiv 버전**: v1과 v2를 같은 책의 다른 판으로 볼지(추천: 같은 책, 최신 판으로 본문 교체, 이전 판 기록 유지), 다른 책으로 볼지
- **옵시디언 링크**: 내보낼 때 참조 카드와 관련 칸을 `[[칸 이름]]` 링크로 넣을지. 추천: 넣음. 옵시디언 그래프에서 칸 사이 연결이 보인다

리스크
- 판정 기준(4-1, 4-2, 4-3)이 초기값이라 틀릴 수 있다 → 스파이크에서 사람 판단과 맞춰보고 조정
- 탭 본문과 서버 결과가 다른 판(예: 기사 수정 전후)일 수 있다 → 캡처 날짜를 둘 다 기록
- 한국어 검색 품질 → 쓰면서 고도화
- 가져오기 200권의 첫 분류 비용과 시간 → 스파이크에서 실측, 진행률 화면으로 기다림을 보여줌
- 혼자 만드는 규모 대비 구성 요소가 많다 → MVP는 서버 렌더링(Playwright)과 GROBID를 빼고 시작할 수 있는지 스파이크로 판단
