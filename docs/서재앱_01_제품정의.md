**서재앱 01 제품정의**

이 문서가 답하는 질문: 왜 만들고, 누가 쓰고, 기존 도구와 무엇이 다른가
현재 기준 문서. 결정이 바뀌면 이 자리에서 고친다. 바뀐 이력은 `서재앱_00_허브.md` 결정 로그에 남긴다.
버전 구분(MVP / 다음 / 그다음)은 `서재앱_03_기능과흐름.md`에만 적는다.

---

**1. 한 문장**

**쓸수록 내 기준을 아는 사서가 생기는 서재**

- 해석(메모와 하이라이트가 남는 것)과 성장(분류 기준이 자라는 것)은 이 문장 안에 들어간다
- 이전 문장
  - "사라지지 않고, 알아서 꽂히고, 한눈에 보이는 논문·기사 서재": 세 약속이 나열되어 하나로 읽히지 않았다
  - "원문보다 내 해석이 남고, 쓸수록 내 기준으로 자라는 서재": 해석과 성장 두 축. 크롬 확장으로 바뀌며 사서와의 관계를 앞에 세우는 쪽으로 좁혔다

형태: 크롬 확장. 새 탭이 곧 서재이고, 담기는 북마크로 한다. 뒤에서는 우리 서버가 수집·분류·저장을 맡는다 (상세는 05)

**2. 누가 쓰나**

- 나 + 친구 한두 명. 친구에게 책 한 권 단위로 공유하는 기능은 셋째 단계
- 공유 방식: 초대한 소수에게만, 원문은 링크로, 내 메모와 정리는 함께. 공개 링크와 검색 노출은 막는다
- 자기개선 루프는 사람마다 따로 돌린다. 친구의 신호가 내 분류 기준을 바꾸지 않게 하고, 공유는 책을 주고받는 기능으로만 둔다

사용자가 나 하나인 것의 장점
- 자기개선 루프가 깨끗하게 돈다. 신호를 주는 사람이 하나라 기준이 섞이지 않는다. MultEval의 "사람끼리 기준 맞추기" 문제가 없고, EvalGen도 개발자 한 명의 판단에 평가자를 맞추는 구조다
- 사용자 수 없이도 성과를 숫자로 보여줄 수 있다. 포트폴리오에서 보여줄 것은 개선 과정이다
  - 자동 분류된 책을 다른 칸으로 옮긴 비율 (예: 1주차 40% → 8주차 12%, 숫자는 예시)
  - 요약을 다시 생성하거나 고친 비율의 변화
  - 들어오는 글 버전별 정답지 유지율

한계
- 내 취향에만 맞춰져 다른 사람에게 통하는지 알 수 없다
- A/B 테스트나 퍼널 분석은 할 수 없다

나중에 넓힐 방법
- 각자 설치해서 쓰는 도구로 공개: 서비스가 대신 저장하는 구조가 아니라, 각 사용자가 자기 저장소에 자기 글을 저장하는 도구로 배포한다. 확장은 각자 설치하는 형태라 이 구조에 가깝다. 이것도 공개 전에 전문가 확인이 필요하다
- 친구 2~3명이 들어오면 "내 취향에만 맞춰짐" 한계가 조금 풀리고, 친구가 공유받은 글을 자기 서재에 담았는지 같은 신호도 생긴다

**3. 왜 만드나**

| 서재에서 하는 일 | 이 앱이 해주는 것 | 기존 도구의 빈틈 |
|---|---|---|
| 모으기 | 북마크 하나면 원문까지 보관 | 북마크는 링크만 남아서 사라지면 끝 |
| 꽂기 | 알아서 주제 칸에 꽂고, 내가 옮길수록 기준이 글로 쌓임 | 폴더는 직접 정리해야 해서 결국 안 하게 되고, 학습형 추천은 무엇을 배웠는지 보이지 않음 |
| 둘러보기 | 새 탭의 책장으로 한눈에. 어떤 주제가 두꺼워졌는지, 오래 안 펼친 책은 뭔지 | 목록형 도구는 쌓일수록 안 보임 |
| 꺼내 쓰기 | 칸을 통째로 꺼내 요약과 내 메모로 빠르게 복습 | 저장한 걸 다시 찾기 어려움 |
| 빌려주기 | 친구에게 책 한 권 건네듯 메모와 링크 공유 | 링크만 보내면 내가 왜 좋았는지가 빠짐 |
| 들여오기 | 사서가 내 칸 기준으로 논문·리포트 같은 묵직한 자료를 구해옴 (수서, 4-5) | 추천 서비스는 블로그 글 중심이라 깊이와 다양성이 아쉬움 |

특히 중요한 세 가지
1. 쌓아두기만 하는 문제: "안 보고 쌓아둔 기사·논문". 초록 카드로 훑고 필요한 것만 깊게 읽는 2층 구조로 푼다
2. 쓸수록 나를 닮는 분류: 몇 달 쓰면 칸 구성이 내 관심사 지도가 된다. 폴더 구조는 처음 만든 모양에서 멈춘다
3. 사라지지 않는 서재: 웹페이지는 10년이면 38%가 사라진다(퓨리서치 2024). 서비스도 사라진다. Pocket은 2025년 7월 종료, Omnivore도 종료. 원문을 담아두는 서재는 링크도 서비스도 사라져도 남는다. 이 약속은 앞의 두 가지를 받치는 바닥이다 (내 해석이 남으려면 원문이 사라지면 안 되므로)

**4. 무엇이 다른가**

**4-1. 포지셔닝의 네 축**

읽기 도구 시장(요약·번역·질의응답)에서는 겨루지 않는다. 읽은 뒤에 남는 것과, 분류 기준이 내 것이 되어가는 과정으로 자리를 잡는다.

| 축 | 내용 | 역할 |
|---|---|---|
| 관계 | 사서가 묻고, 내가 답하면 분류 기준이 바뀌고, 믿을 만해지면 권한이 넘어감 | 앞에 세우는 말 |
| 성장 | 사용 신호로 내 분류 기준이 자람. 그 과정이 칸마다 "이 칸에 들어오는 글"로 남고 검증·되돌리기가 됨. 자란 기준으로 사서가 밖의 자료도 구해옴(수서) | 관계가 눈에 보이는 증거. MVP의 핵심 |
| 해석 | 하이라이트·메모·용어 설명이 서재의 본체 | 사서가 배우는 재료 |
| 기억 | 자리로 떠올리는 공간 감각 (mind palace) | 붙잡아두는 장치. 자리 안정성 원칙으로 지킴 (02) |

이 포지셔닝이 만드는 것
- 첫 화면의 주인공은 책장이 아니라 사서다. 새 탭을 열 때마다 사서가 무언가 하고 있다
- 정답지가 약속이 된다. "스무 권이면 당신의 사서가 생깁니다"
- 서재 기록은 부속이 아니라 핵심이다. 사서가 나를 얼마나 알게 됐는지 보는 자리로, 따로 한 페이지인 사서 데스크에 둔다 (04 S34)
- 3D 서재는 배경이고 관계가 앞에 선다

**4-2. 기존 도구와 비교 (2026-09-24 확인, 서핏은 2026-09-26 추가)**

| 도구 | 하는 것 | 서재앱과의 관계 |
|---|---|---|
| Raindrop | 북마크 관리. Pro 요금제에 AI 추천(내가 만든 컬렉션·태그를 보고 새 북마크의 자리를 제안하고, 내가 고른 것으로 계속 배움. 추천만 하고 확정은 사람이 함). Pro 웹 아카이브(저장 후 몇 분 안에 페이지를 받아 보관, 전문 검색 가능. 로그인이 필요한 페이지는 못 가져옴) | 가장 가까운 도구. 학습하는 분류가 이미 있다. 차이는 학습 과정이 보이는가 |
| Readwise Reader | 읽기·하이라이트·요약(Ghostreader). 브라우저 확장으로 저장하면 보고 있는 화면 전체를 받아 페이월 기사도 저장됨 | 로그인 기사 저장은 여기서 이미 한다. 서재앱에서는 차별점이 아니라 기본기 |
| 옵시디언 | 마크다운 파일 소유와 링크, 플러그인 생태계. 웹 클리퍼는 보던 페이지를 내 볼트에 파일로 저장 | 정면으로 겨루지 않고 공존. 모으기와 꽂기는 사람이 한다 |
| 서핏 | 새 탭을 바꿔 직군별 아티클을 매일 추천(하루 1,000개 채널에서 선별). 커리어 기록 기능. 사용자 약 2만 명 | 방향성 참고 (4-5). 서핏은 밖의 글을 데려오고, 서재앱은 담은 글을 정리한다 |
| Momentum·Tabliss | 새 탭 꾸미기 | 정리는 사람이 한다 |
| Toby·Workona | 탭과 북마크 정리 | 기준은 사람이 만든다 |
| Hypothesis·Glasp·Liner | 웹 위 하이라이트 | 분류와 성장은 없다 |
| Pocket·Omnivore | 나중에 읽기 | 둘 다 종료. 서비스가 사라지면 서재도 사라진다는 사례 |

정정 기록: 이전 문서에는 "북마크를 사서가 분류하고, 내가 고치면 기준이 자라는 구조는 아직 없다"고 적었다. Raindrop AI 추천이 이미 이 구조라서 틀린 판단이었다. 로그인 기사 저장도 Readwise가 이미 한다.

**4-3. 그래서 서재앱의 차이**

**학습 과정이 보이고, 검증되고, 되돌릴 수 있는 분류**

Raindrop의 학습은 모델 안에서 조용히 일어난다. 왜 거기를 추천했는지, 무엇을 배웠는지, 되돌릴 수 있는지가 보이지 않는다. 서재앱은 그 과정을 밖으로 꺼낸다.

- 배운 기준이 칸마다 "이 칸에 들어오는 글"로 남아서 읽고 고칠 수 있다
- 규칙이 바뀌기 전에 "이 책 5권도 옮겨져요"를 먼저 보여준다
- 정답지 20권으로 회귀 확인을 하고, 버전을 되돌릴 수 있다
- 매번 같게 틀리는 것(결정론적)은 규칙으로, 돌릴 때마다 흔들리는 것(확률적)은 참조 카드·임시서가로 보낸다

기본기로 갖추는 것 (차별점은 아님)
- 원문 보관, 전문 검색
- 북마크하는 순간 보고 있던 탭의 본문을 떠두고 서버 수집 결과와 비교해 나은 쪽을 저장
- 로그인해야 보이는 페이지는 담기 전에 물어봄. 혼자 쓰는 동안 내 사용(예: 잡코리아 JD)으로 테스트하고, 공개 전에 약관·법을 다시 판단
- 담지 않는 사이트(메일, 은행·결제, 문서 도구 등 앱 기본값 + 내가 추가)는 담지 않음. 무엇을 모으는지 설치할 때 안내

솔직한 판단: 제품 경쟁력으로는 이 차이가 약할 수 있다. 대부분의 사람은 추천이 맞기만 하면 이유까지 궁금해하지 않는다. 이 앱의 목표는 기존 도구를 대체하는 것이 아니라, 내가 실제로 쓰면서 분류 품질이 어떻게 나아지는지를 숫자로 보여주는 것이다. 그래서 수집 품질이나 기능 수는 겨룰 대상이 아니다. "내가 쓰려고 직접 만든 Raindrop, 대신 학습 과정이 보이는"도 이 앱을 설명하는 한 방법이다.

**4-4. 옵시디언과의 관계**

- 옵시디언의 힘은 마크다운 파일 소유 구조와 플러그인 생태계, 커뮤니티다
- 옵시디언이 약한 자리: 모으기(클리퍼 설정과 정리가 번거로움), 꽂기(폴더·태그를 직접 관리), 보기(책장 같은 시각 구조 없음)
- 서재앱의 자리: 수집·분류·시각화 앞단 + 사서. 깊은 편집과 연결은 옵시디언
- 저장 형식을 마크다운으로 맞춰 공존한다. Phase 앱 구상(로컬 마크다운 + GitHub 동기화)도 이 길과 같아져 따로 합칠 필요가 없어졌다 (내보내기 방식은 05)

**4-5. 방향성 참고: 서핏과 수서**

서핏에서 가져오는 것
- 새 탭을 하루에 수십 번 여는 습관 위에 서비스를 올린 점. 서핏을 새 탭으로 두면 별 고민 없이 읽을거리를 찾을 수 있다. 서재앱이 크롬 확장으로 바꾼 이유와 같은 판단이다

서핏에서 아쉬운 점
- 블로그 글 중심이라 깊이와 다양성이 부족하다

서재앱이 기대하는 것
- 관심사 기반 큐레이션에 더해, 논문·리포트처럼 묵직한 외부 자료를 사서가 찾아온다
- 서핏은 발견(밖에서 데려옴)이 중심이고, 서재앱은 소화(담은 것을 정리하고 기준을 키움)가 중심이다. 서핏에서 보고 북마크한 글이 서재앱으로 들어오는 흐름도 자연스럽다

수서 (관심사 기반 외부 자료 추천)
- 도서관에서 사서가 장서 기준에 맞춰 자료를 골라 들여오는 일을 수서라고 한다. 기능 이름도 여기서 온다
- 기준은 MVP에서 쌓는 들어오는 글이다. 칸마다 "여기 들어오는 것"을 적은 글이 그대로 검색 기준이 되고, 내가 고칠수록 구해오는 자료도 같이 정확해진다. MVP가 수서의 재료를 만든다
- 출처는 공개 API와 라이선스가 분명한 곳 위주: arXiv, Semantic Scholar(논문 추천 API), OpenAlex, 오픈액세스 저널, 연구소·기업 리서치 블로그 RSS. 기사 크롤링보다 저작권 쪽이 깔끔하다
- 수서해온 자료를 내가 서재에 담으면 가장 강한 신호가 된다
- 기존 기능과의 구분: 저녁 큐레이션은 내 서재 안의 책을 다시 꺼내고, 상호대차는 읽다가 눌렀을 때만 밖에서 찾아온다. 수서는 사서가 먼저, 내 기준으로 밖에서 구해온다
- 수서 로직(검색 기준, 출처, 하루 몇 권, 평가)은 MVP가 돌아간 뒤에 설계한다. MVP에서 기준이 제대로 자라는지 확인되어야 그 기준으로 밖을 찾는 일도 생각할 수 있다

**5. 사용 장면**

선택한 장면
1. 출근길에 링크드인에서 본 논문을 폰 크롬으로 북마크했더니, 회사에서 컴퓨터를 켤 때 "LLM 평가" 칸에 꽂혀 있음 (크롬 계정 동기화로 PC에 내려와 담김)
2. 주말에 새 탭을 열어보니 3주 동안 쌓인 글이 7개. 초록 카드로 훑고 2개만 깊게 읽음
4. 논문을 읽다가 모르는 용어를 그 책 안에 메모로 남겨둠
5. 몇 달 뒤 "평가" 칸이 너무 두꺼워서 "평가 기준"과 "평가 자동화"로 나눔
8. 책 한 권을 다 읽고 나니, 내 서재 안에서 같이 읽으면 좋은 책 두 권을 옆에 꺼내줌
추가. 저녁에 새 탭을 열면 "오늘 이 책은 어떠세요?" 큐레이션이 와 있음
추가. 아침에 새 탭을 여니, 사서가 "LLM 평가" 칸 기준으로 이번 주 나온 논문 두 편을 구해와 신착 서가에 올려둠 (수서)

선택하지 않은 장면 (후보로 보관)
3. 면접 전날 "LLM 평가" 칸을 통째로 꺼내서 요약과 내 메모로 복습함 → 칸 이어 읽기와 직접 만드는 전시로 일부 살아남음
6. 친구가 비슷한 고민을 하길래, 내 메모를 붙인 논문 한 권을 빌려줌
7. 반년 전에 담은 기사에 "원본은 사라졌고 내 서재에만 남아 있어요" 표시가 떠 있음

선택 장면의 흐름: 들여오기(수서) → 담기(1) → 소화하기(2, 저녁 큐레이션) → 기록하기(4) → 정리하기(5) → 연결하기(8)

장면별 필요한 기능과 쌓이는 신호

| 장면 | 필요한 기능 | LLM이 하는 일 | 쌓이는 신호 |
|---|---|---|---|
| 1. 북마크하면 알아서 꽂힘 | 북마크 생성 감지, 원문 캡처, 메타데이터 추출 | 주제 분류, 칸 배치 | 내가 다른 칸으로 옮김 |
| 2. 쌓인 글을 초록 카드로 훑음 | 안 읽은 책 모아보기, 초록 카드, 읽기 뷰어 | 초록 카드 생성(기사는 3줄 요약) | 카드만 보고 넘김 / 읽기로 들어감 |
| 4. 모르는 용어를 책 안에 메모 | 하이라이트, 메모, 용어 설명 | 용어 설명 초안 | 그대로 둠 / 고침 / 지움 |
| 5. 두꺼운 칸을 둘로 나눔 | 칸 나누기·합치기, 책 일괄 이동 | 나누는 방법 제안 | 제안 수락 / 직접 다르게 나눔 |
| 8. 다 읽으면 같이 읽을 책을 꺼내줌 | 읽음 표시, 관련 책 추천 | 본문끼리 비교해 비슷한 책 찾기 | 추천을 열어봄 / 무시함 |
| 추가. 저녁 "오늘 이 책은 어떠세요?" | 새 탭 사서 자리의 카드 또는 크롬 알림 | 오늘의 책 고르기, 이유 한 줄 | 열어봄 / 넘김 / "이런 건 그만" |
| 추가. 아침 수서 | 외부 자료 검색, 신착 서가 | 들어오는 글로 검색 기준 만들기, 관련성 판정, 이유 한 줄 | 담음(가장 강함) / 열어만 봄 / 넘김 |

- 5번은 criteria drift가 앱 안에서 일어나는 장면이다. 칸이 두꺼워지면 사서가 나누는 방법을 제안하고 내가 받아들이거나 고치는 mixed-initiative 방식
- 장면별로 어느 버전에 들어가는지는 03에 있다

**6. MVP의 목표와 성공 기준**

MVP 한 문장: **북마크하면 알아서 꽂히고, 내가 고칠수록 분류 기준이 글로 쌓이며, 그 변화를 검증하고 되돌릴 수 있는 서재**

- MVP는 4-3의 차이 하나를 증명하는 데 집중한다
- MVP에서 쌓인 들어오는 글이 다음에 붙일 수서의 기준이 된다. MVP가 먼저 돌아가야 수서 로직도 설계할 수 있다
- 범위(넣는 것과 미루는 것)와 MVP 다음 순서는 03에 있다

성공 기준: 4~8주 동안 직접 쓰면서
- 내가 칸을 옮기는 비율이 줄어든다
- 규칙을 바꿔도 정답지 유지율이 떨어지지 않는다

남은 리스크: 혼자 쓰는 데이터라 표본이 작다. 숫자는 추세로 보여주고, 사례(어떤 이동이 어떤 규칙이 되었는지)를 함께 남긴다

**7. 상업화에 대한 현재 판단**

- 읽기·보관 서비스들(Pocket, Instapaper, Readwise Reader, Matter, Raindrop)은 서버에 본문을 저장하면서 유료로 운영된다. 사용자 저장소 연결(BYO)은 법적으로 더 깨끗하지만 연결 단계 이탈과 지원 비용이 커서 제품으로는 불리하다
- 지금은 저장 계층(원문 저장소와 서비스 저장소)을 코드에서 분리해두는 것까지만 한다 (05)
- 확장으로 바뀌면서, 상업화 시 "확장이 뜬 본문을 사용자 쪽 저장소에 넣고 서버는 메타·메모·분류만 받는" 구조가 가능해졌다. 옵시디언 웹 클리퍼에 가까운 모양이다
- 상업화의 병목은 저작권보다 "왜 돈을 내는가"다. 개인 구독은 기존 도구 대비 우위가 약하고, 니치(대학원생·연구자)나 기관·팀 쪽이 지불 의사와 저작권 양쪽에서 더 깔끔하다
- 유료로 간다면 설계 방향(현재는 보류): 관련 기사는 요약 없이 제목·매체·날짜·링크 + "내 서재의 어느 글과 왜 관련 있는지" 한 줄. 요약을 판다면 언론사 API·제휴, 오픈액세스 논문처럼 라이선스 확인된 소스로 범위를 좁힌다. 수서도 같은 기준으로 출처를 고른다
- 순서: MVP 완성 → 8~12주 직접 사용 → 사용 데이터를 근거로 판단. 공개·유료화 전에는 저작권 전문가 확인 (판단 근거는 99)

**8. 포트폴리오·면접 포인트**

- 한 줄: "전공 지식으로 분류 체계를 설계하고, 사용자 행동으로 LLM 분류가 스스로 나아지게 하되, 그 과정을 보이고 검증하고 되돌릴 수 있게 만든 앱"
- 전공 지식(분류 체계, 통제 어휘, 문헌적 보증, 웹 아카이빙, LOCKSS, 수서)을 제품 설계에 적용
- 결정론적 실패는 사용자 확인을 거쳐 규칙으로, 확률적 실패는 참조 카드·임시서가로 나눈 처리 경로
- LLM 판단(주제)과 코드 검증(메타데이터)을 설계 단계에서 분리
- 확률적 실패의 흔들림을 버리지 않고 참조 카드 배치에 사용
- 분류 결과를 내가 채점한 정답지가 별도 라벨링 없이 회귀 테스트 세트가 되는 구조
- 사용자 행동으로 judge 판단까지 검증하는 구조 (전시 서가)
- 큐레이션 이유 문구에서 사실값(코드)과 문장(LLM)을 나눠 코드로 검증
- 손글씨 이름표 칸 수로 사람-AI 신뢰 변화를 수치화
- 사용자 규모 대신 개선 과정 지표(칸 이동 비율, 요약 재생성 비율, 버전별 정답지 유지율)로 성과 제시
- 트리거 수치를 로그 근거로 조정하고 정책 버전으로 기록
- 사람이 만든 것과 AI가 만든 것을 손글씨 / 인쇄 라벨로 일관되게 구분한 표기 원칙
- 기획과 디자인의 경계를 "동작·규칙·데이터가 바뀌는가"로 나눠 순서대로 진행
- 링크 소실 문제를 웹 아카이빙 관점으로 설계 (국립중앙도서관 OASIS 사업), 디지털 보존 원칙(LOCKSS)으로 저작권 제약과 링크 소실을 같이 풂
- 만들던 중에 방향을 튼 판단과 근거 (폰 PWA → 크롬 확장). 무엇을 보고 바꿨고 무엇을 지켰는지
- 기존 도구 조사로 차별점을 정정한 과정. 예상 질문 "Raindrop도 이거 하던데요?" → "알고 있고, 블랙박스 학습과 보이는 규칙·회귀 검증의 차이를 설계했다"
- 욕심나는 기능(수서, 하이라이트)을 MVP 뒤로 미루고, MVP가 그 기능의 재료(들어오는 글)를 만들도록 순서를 설계한 판단
