**1. 포지셔닝**

읽기 도구 시장(요약·번역·질의응답)에서는 겨루지 않는다. 읽은 뒤에 남는 것과, 분류 기준이 내 것이 되어가는 과정으로 자리를 잡는다.

한 문장 콘셉트: **쓸수록 내 기준을 아는 사서가 생기는 서재**

세 축과 각각의 역할

| 축 | 내용 | 역할 |
|---|---|---|
| 관계 | 사서가 묻고, 내가 답하면 분류 기준이 바뀌고, 믿을 만해지면 권한이 넘어감 | 앞에 세우는 말 |
| 해석 | 하이라이트·메모·용어 설명이 서재의 본체 | 사서가 배우는 재료 |
| 성장 | 사용 신호로 내 분류 기준이 자람 | 관계가 눈에 보이는 증거 |
| 기억 | 자리로 떠올리는 공간 감각 | 붙잡아두는 장치. 첫 버전은 자리 안정성만 |

이 포지셔닝이 만드는 것
- 첫 화면의 주인공은 책장이 아니라 사서다. 새 탭을 열 때마다 사서가 무언가 하고 있다
- 20권 정답 세트가 약속이 된다. "스무 권이면 당신의 사서가 생깁니다"
- 서재 기록 화면이 부속이 아니라 핵심이다. 사서가 나를 얼마나 알게 됐는지 보는 화면이다
- 3D 서재는 배경이고 관계가 앞에 선다

비교
- Momentum·Tabliss: 새 탭을 꾸민다. 정리는 사람이 한다
- Toby·Workona: 탭과 북마크를 정리한다. 기준은 사람이 만든다
- Raindrop: 북마크를 관리한다. 분류는 사람이 한다
- Hypothesis·Glasp·Liner: 웹에 하이라이트를 남긴다. 분류와 성장은 없다
- 옵시디언: 파일 소유와 링크. 모으기와 꽂기는 사람이 한다

북마크를 사서가 분류하고, 내가 고치면 기준이 자라는 구조는 아직 없다.

자리 안정성 원칙 (첫 버전에 넣는 기억 장치)
- 칸 안 배열은 담은 순서 고정. 자동 재정렬을 기본값으로 쓰지 않음
- 규칙으로 책이 옮겨지려면 사용자 승인 필요
- 이동 흔적: 원래 자리에 "이 책은 ○○ 칸으로 옮겨졌어요"를 일주일 남김
- 책을 닫으면 그 책이 꽂힌 자리가 보이는 상태로 복귀
- 칸 순서가 저절로 바뀌지 않음
- 어떤 기능을 넣든 "이게 책의 자리를 흔드나?"를 먼저 본다

다음 버전으로 둘 기억 기능: 모양으로 찾기(색·시기·포스트잇 유무 필터), 서재 산책, 자리의 이야기

옵시디언과의 관계
- 옵시디언의 힘은 마크다운 파일 소유 구조와 플러그인 생태계다. 정면으로 겨루지 않는다
- 옵시디언이 약한 자리: 모으기(클리퍼 설정과 정리가 번거로움), 꽂기(폴더·태그를 직접 관리), 보기(책장 같은 시각 구조 없음)
- 서재앱의 자리: 수집·분류·시각화 앞단 + 사서. 깊은 편집과 연결은 옵시디언
- 저장 형식을 마크다운으로 맞춰 공존한다 (5절)

상업화에 대한 현재 판단
- 읽기·보관 서비스들은 서버에 본문을 저장하면서 유료로 운영된다. 사용자 저장소 연결(BYO)은 법적으로 더 깨끗하지만 연결 단계 이탈과 지원 비용이 커서 제품으로는 불리
- 지금은 저장 계층을 코드에서 분리해두는 것까지만 한다
- 상업화의 병목은 저작권보다 "왜 돈을 내는가". 니치나 기관·팀 쪽이 지불 의사와 저작권 양쪽에서 더 깔끔함
- 순서: 첫 버전 완성 → 8~12주 직접 사용 → 사용 데이터를 근거로 판단

**2. 읽기 기준선**

읽기는 차별점이 되지 못해도 없으면 나머지가 성립하지 않는 바닥이다. 하이라이트와 메모는 전부 본문 위에서 일어나므로, 본문이 깨지면 해석도 성장도 재료가 생기지 않는다. 경쟁하지는 않되 기준선은 숫자로 관리한다.

읽기 등급은 `서재앱_화면설계서.md` 0절에 정의되어 있다 (A: 본문 깨끗 / B: 화면만 남김 / C: 원문 못 가져옴).

출처별 경로 사다리

| 출처 | 1순위 | 2순위 | 3순위 | 마지막 |
|---|---|---|---|---|
| 기사 | 서버가 HTML을 받아 본문 추출 | 확장이 내가 보고 있는 화면의 본문을 보냄 | 서버에서 브라우저 렌더링 후 추출 | 링크 + 아카이브 주소 |
| 로그인·유료 기사 | 확장이 보고 있는 화면의 본문을 보냄 (A등급) | | | 링크 + 메모 |
| arXiv 논문 | arXiv HTML 버전 | ar5iv | PDF 텍스트 추출 | 원문 PDF 뷰어 |
| 오픈액세스 논문 | 출판사 HTML | 학술 PDF 구조 분석 | PDF 텍스트 추출 | 원문 PDF 뷰어 |

확장이 생기면서 2순위가 강해졌다. 서버가 못 가져오는 기사도 내가 열어둔 상태라면 본문을 확보할 수 있다. 다만 자동으로 되지는 않으므로 "내가 열어둔 상태에서 담기"가 전제다.

읽기 모드 두 개
- 텍스트 모드(기본): 뽑아낸 본문. 하이라이트·메모가 됨
- 원문 모드: 원본 그대로. 표·수식 확인용. 원문 페이지에서 직접 하이라이트하는 것과는 다르다 (그쪽은 확장 도구 모음)
- 품질이 낮으면 "읽기 품질 낮음" 표시 + 다시 가져오기

관리할 지표
- 깨끗하게 열린 비율 (매체별, 유형별, 경로별)
- 확장 경로로 넘어간 비율 (서버 수집이 실패한 비율)
- 다시 가져오기를 누른 비율
- 텍스트 모드에서 원문 모드로 넘어간 비율
- 하이라이트가 하나도 안 남은 책의 비율

현실적인 기대
- 일반 기사: 잘 되지만 본문 외 요소(관련 기사, 구독 배너, 사진 설명, 기자 소개, 중간 광고)가 섞임
- arXiv 논문: HTML이 있으면 좋음. 오래된 논문·복잡한 수식은 변환 실패도 있음
- 그 외 논문 PDF: 어려움. 2단 조판에서 문장 순서가 섞이고 각주가 끼어듦
- 로그인·유료 기사: 확장 경로로 해결 가능

읽기 품질 스파이크 (측정부터, 작업 목록 10번)
1. 평소 담을 법한 링크 30개 (기사 20, arXiv 5, 그 외 논문 PDF 5)
2. 경로별로 돌려보기: 서버 단순 수집 / 서버 렌더링 후 수집 / 확장이 보낸 화면 본문
3. 채점: 본문 누락 / 문장 순서 / 본문 외 혼입(몇 개, 어느 위치) / 깨진 글자 / 그림·표 보존 / 읽을 만한가
4. 결과로 기준선과 첫 버전 대상 범위 확정

세 경로를 비교하는 것이 스파이크의 핵심 질문이다. 서버 렌더링(무거움)이 정말 필요한지, 확장 경로로 충분한지를 본다.

**3. 이미지 처리**

| 대상 | 방식 |
|---|---|
| 기사 사진 | 담을 때 받아 저장(지연 로딩 주소 처리, 가로 1600px·가벼운 형식으로 변환). 캡션 함께 저장. 로고·아이콘·투명 픽셀은 크기·비율로 걸러냄 |
| arXiv HTML 논문 | 그림 파일이 따로 있어 그대로 가져옴 |
| 그 외 논문 PDF | 텍스트 모드에는 "그림 1이 여기 있었어요" 자리표시, 누르면 원문 모드의 해당 페이지로 |

그림 설명
- 순서: 원문 캡션이 있으면 그것 → 없으면 LLM이 봄 → LLM이 쓴 설명에는 "사서가 본 그림" 표시
- 담을 때 전부 만들지 않고 "이게 뭐야?"를 누를 때만 만들고 저장
- 그림 종류별 난이도: 사진은 무난, 다이어그램은 대체로 가능, 그래프·표는 축과 수치 오독 위험
- 프롬프트에서 수치를 단정하지 않게 하고 원본 보기 버튼을 항상 함께 둠
- 신호: 설명을 보고 원본을 열어봤는지, 설명을 고쳤는지

공유할 때는 이미지를 빼고 내 메모와 링크만 보냄

**4. 저장 구조 (상업화 대비)**

두 저장소를 논리적으로 분리한다. 지금은 같은 서버에 있어도 경로와 테이블을 따로 둔다

| 원문 저장소 (소유자: 사용자) | 서비스 저장소 (소유자: 서비스) |
|---|---|
| 본문 텍스트, 이미지, PDF 스냅샷 | 메타데이터, 원본 링크, 아카이브 주소 |
| | 내 메모·하이라이트, 책 전체 메모 |
| | 그림 설명, 용어 설명, 요약 |
| | 분류 결과, 칸 구조, 범위주기, 신호 로그 |

지킬 네 가지
1. 원문 저장소와 서비스 저장소를 코드와 데이터 모델에서 분리
2. 화면은 원문이 없어도 성립하게 만든다
3. 이미지는 자리표시 + 설명을 기본으로, 원본은 "원본 보기" 한 단계 안에
4. 서비스가 새로 만든 텍스트(요약, 그림 설명, 용어 설명)는 서비스 저장소에. 상업화해도 남는 자산

이미지를 숨기는 것 자체는 저작권 판단을 바꾸지 못한다. 기준은 누가 저장하고 돈을 받느냐다. 지금은 혼자 쓰므로 사적 이용 범위 안이고, 공개·유료화 시점에 원문 저장소만 사용자 쪽으로 옮긴다

확장으로 바뀌면서 달라진 점
- 브라우저에서 본문을 확보할 수 있으므로, 상업화 시 "확장이 수집해 사용자 저장소에 직접 넣고 서버는 메타만 받는" 구조가 가능해진다. 서버를 원문이 거치지 않는 형태로 만들 여지가 커졌다
- 첫 버전에서는 서버 저장 그대로 두고, 저장 계층 분리만 지킨다

**5. 옵시디언과 북마크**

옵시디언: 마크다운으로 저장해 공존한다. 칸이 폴더, 책 한 권이 파일. 첫 버전은 내보내기(zip), 다음 버전에 깃허브 비공개 레포 동기화. 양방향은 나중 (상세는 기능목록 문서 8절)

크롬 북마크: 첫 버전의 주 입구
- 확장이라 크롬 북마크를 직접 읽고 쓸 수 있다 (공개 API가 없다는 이전 판단은 확장에는 해당하지 않는다)
- 설치 시점을 기준선으로 삼아, 이후 새 북마크만 자동으로 담는다
- 기존 북마크는 목록만 읽어두고, 사서가 폴더 단위로 가져오기를 제안한다
- 가져오기 전에 링크 생존을 확인하고, 죽은 링크는 따로 모아 아카이브를 권한다
- 북마크를 지우면 보존 서고로, 같은 주소 재북마크는 기존 책에 병합
- 북마크와 서재는 따로 운영되고 한 방향으로 흐른다. 크롬 북마크 구조는 사용자의 기존 습관이므로 손대지 않는다

노션 가져오기는 후보로 남는다

여기서 보이는 것
- 초록 카드가 길목이다. 서재, 칸, 안 읽은 책, 임시서가, 검색, 보존 서고에서 모두 초록 카드로 들어온다
- 읽기 뷰어가 가장 복잡하다. 선택 메뉴, 용어 설명, 그림 설명, 상호대차, 메모, 읽기 모드가 모두 여기 걸린다
- 사서 자리가 새 탭에 하나뿐이다. 질문, 첫 20권 확인, 수집 결과 보고가 모두 여기로 모인다. 하루 2개 상한도 여기서 지켜진다
- 담는 입구가 셋이다. 북마크, 확장 아이콘, 원문 위 도구 모음. 모두 같은 수집 파이프라인으로 들어간다

**8. 온보딩·사서·설정**

온보딩 순서와 필수·선택

| 단계 | 필수 | 건너뛰면 |
|---|---|---|
| 확장 설치 | 필수 | |
| 로그인 (이메일 → 서버 발급 키를 확장에 저장) | 필수 | 서버 저장이라 건너뛸 수 없음 |
| 이름 | 필수 | 비우면 다음으로 못 넘어감. 입력하면 사서가 한 번 불러줌 |
| 관심 주제 (칩 + 직접 입력) | 선택 | 칸 없이 시작. 임시서가에 3권 모이면 칸 제안 |
| 북마크 폴더 선택 | 선택 | 기본은 모든 새 북마크를 담음 |

크롬 알림 권한은 저녁 큐레이션을 붙일 때 함께 요청한다

사서 UI: 새 탭의 사서 자리
- 사서는 집사 고양이. 파츠 조합으로 상태를 표현한다: 귀(평소/쫑긋/눕힘), 눈(뜸/반달/감음/곁눈질), 꼬리(말림/살랑/곧게), 손(빈손/책/돋보기/리본)
- 새 탭을 열 때마다 무언가 하고 있다: 아침 인사, 수집 중이면 책을 안고 걷기, 물어볼 게 있으면 고개를 들고 말풍선, 실패가 있으면 귀를 눕힘, 아무 일 없으면 졸기, 저녁이면 램프
- 말을 거는 건 하루 두 번까지. 조용한 상태가 기본
- 사서가 맡는 것: 첫 20권 확인, 규칙 질문, 임시서가 알림, 북마크 가져오기 제안, 수집 결과 보고, 나중에 전시·큐레이션
- 그래픽 예산은 사서에 몰고, 책장과 목록은 단순한 도형과 글자로 간다

방금 담은 책 알리기
- 새로 꽂힌 책이 있는 칸이 은은하게 빛남
- 그 칸을 열면 해당 책에서 카툰풍 별 반짝임(0.8초). 본 뒤에는 사라짐
- 사서의 보고를 누르면 그 자리로 이동하며 반짝임
- 신간 띠지는 "아직 안 읽음", 반짝임은 "방금 들어옴"

설정 화면 구성

| 묶음 | 내용 |
|---|---|
| 읽기 | 글자 크기, 줄 간격, 다크 모드, 그림은 설명으로 보기 |
| 서재 기록 | 담은 책 수, 칸 이동 비율, 요약 재생성 비율, 읽기 품질, 사서 제안 수락률 |
| 저장 | 내보내기, 백업 상태, 보존 서고 |
| 수집 | 수집 실패 목록, 자동 담기 폴더, 북마크 가져오기 |
| 계정 | 로그인 정보, 로그아웃 |

서재 기록은 숫자만 나열하면 대시보드가 되어 서재 분위기와 따로 논다. 시안 단계에서 "사서의 업무 일지" 형태로 풀어볼 것

범위주기 노출: 온보딩에서는 칸 이름만 확인하고, 첫 확인 카드에서 한 줄로 보여준다
