**1. 출발점: 개인 프로젝트에서 원하는 고도화 방향**

- 평가 결과를 바탕으로 LLM이 프롬프트·로직을 자동으로 수정하는 자기개선 루프
- 정확히는 LLM이 고치는 대상은 주로 프롬프트다. 코드 로직을 마음대로 바꾸는 단계는 아니다
- 두 가지 전제
  - 평가가 먼저 있어야 한다. GEPA도 좋은 출력을 판단하는 지표와 실패 이유를 설명하는 피드백이 있어야 돌아간다. 평가 설계 경험이 가장 중요한 역량
  - 사람이 루프에서 빠지지 않는다. DocWrangler도 사용자가 메모를 남기고 수정안을 받아들이는 구조. 자동 루프는 정해진 기준 안의 최적화는 잘하지만 기준 자체는 바꾸지 못한다. criteria drift는 사람 몫

자기개선 루프 최소 구조
1. 기록: 입력, 중간 단계, 출력 전부 저장
2. 평가: 코드 체크 + LLM judge. 점수와 함께 실패 이유를 자연어로 남기기
3. 반성(reflection): 실패 사례를 묶어 LLM에게 원인 진단과 프롬프트 수정안 요청
4. 검증: 수정안을 별도 검증 세트로 돌려 기존 버전보다 나은지 확인 (회귀)
5. 반영: 승인 후 교체. 프롬프트 버전 관리, 나빠지면 되돌리기
6. 사람 점검: 주기적으로 출력을 직접 보고 평가 기준 갱신

- DSPy에 GEPA가 옵티마이저로 들어가 있어 3~4번을 가져다 쓸 수 있다

미리 알아둘 함정
- 평가자에 맞춰 최적화되는 문제: LLM judge가 좋아하는 방향으로만 바뀌고 실제 품질은 나빠질 수 있다. judge를 사람 판단에 맞추는 작업(EvalGen이 한 일)이 먼저
- 평가 세트에만 맞춰지는 문제: 개선용 사례와 검증용 사례를 분리
- 프롬프트로 안 고쳐지는 실패: 수집 실패, 도구 호출 깨짐은 인프라·구조 문제. 루프에 넣기 전에 "프롬프트로 고칠 것"과 "구조를 고칠 것"으로 나눈다 (처방매핑표 방식)

**2. 콘셉트**

- 지식관리 앱인데 책장처럼
- 주로 담을 것: 논문, 기사
- 주제로 묶고, 가시적으로 예쁘게 관리
- 처음 구상: 추가금을 내면 요약 + 관련 기사(최신순)를 참고로 보여주는 유료 기능 → 저작권 검토 후 유료화 없이 개인 기능으로 전환 (5번 참고)
- 이 대화 자체가 사용 장면의 예시: 논문 하나를 읽고, 모르는 용어를 찾고, 후속 연구를 최신순으로 찾아봄

한 문장 콘셉트 (2026-09-23 갱신): **"쓸수록 내 기준을 아는 사서가 생기는 서재"**
- 이전 문장: "사라지지 않고, 알아서 꽂히고, 한눈에 보이는 논문·기사 서재" → 세 약속이 나열되어 하나로 읽히지 않아 관계 중심으로 좁혔다. 해석과 성장은 새 문장 안에 들어간다

**3. 확정된 결정**

- 사용자: 나 혼자 쓰는 앱. 친구 한두 명에게 책 한 권 단위로 공유 가능 (공유 기능은 셋째 단계)
- 만드는 형태 (2026-09-23): 크롬 확장. 새 탭이 곧 서재. 담기는 북마크, 확장 버튼이 보조. 폰은 iOS 단축어와 나중의 PWA
- 공유 방식: 초대한 소수에게만, 원문은 링크로, 내 메모와 정리는 함께. 공개 링크와 검색 노출은 막음
- 저장 형식: 기사는 본문 텍스트(마크다운) + 메타데이터, 필요하면 PDF나 스냅샷 추가. 논문은 DOI·arXiv ID(버전 포함) + PDF
- 유료 기능: 빼고, 요약과 관련 기사는 개인 기능으로 넣음
- 기반: Hermes는 바꿀 예정. 수집 구조를 새로 설계
- 고도화 방향: 사용 신호(칸 옮기기, 요약 수정 등)로 LLM이 프롬프트를 고치는 자기개선 루프. 사람마다 따로 돌림 (친구 신호가 내 분류 프롬프트를 바꾸지 않게. 공유는 책을 주고받는 기능으로만)
- 분류 체계: 도서관 분류의 원리(계층, 통제 어휘, 패싯)를 가져오고 칸은 관심 분야에 맞게 세분
- 저녁 큐레이션: 여러 기준을 섞고 알고리즘은 사용자에게 숨김. 추천 이유는 **열어본 뒤 공개**
- 원문 링크화는 공유할 때만. 내 서재 안에서는 원문을 그대로 보관하고 요약도 가능
- 책장 구조: 주제 칸 + 시각 기호, 경계 책은 참조 카드, 신간은 띠지 또는 임시서가, 2단 시작, 수정하는 순간 권한이 넘어오는 사서 방식. 사서가 관리하는 칸은 인쇄 라벨, 내가 관리하는 칸은 손글씨 이름표 (상세는 `서재앱_책장구조_260922.md`)

관심 있다고 한 기능: 빌려주기, 아카이빙, 추천

**4. 서재로서의 메리트**

| 서재에서 하는 일 | 이 앱이 해주는 것 | 기존 도구의 빈틈 |
|---|---|---|
| 모으기 | 북마크 하나면 원문까지 보관 | 북마크는 링크만 남아서 사라지면 끝 |
| 꽂기 | 알아서 주제 칸에 꽂고, 내가 옮길수록 더 정확해짐 | 노션·북마크 폴더는 직접 정리해야 해서 결국 안 하게 됨 |
| 둘러보기 | 책장으로 한눈에. 어떤 주제가 두꺼워졌는지, 오래 안 펼친 책은 뭔지 | 목록형 도구는 쌓일수록 안 보임 |
| 꺼내 쓰기 | 주제 칸을 통째로 꺼내 요약과 내 메모로 빠르게 복습 | 저장한 걸 다시 찾기 어려움 |
| 빌려주기 | 친구에게 책 한 권 건네듯 메모와 링크 공유 | 링크만 보내면 내가 왜 좋았는지가 빠짐 |

특히 강한 세 가지
1. 사라지지 않는 서재: 웹페이지는 10년이면 38%가 사라진다(퓨리서치 2024). 서비스도 사라진다. Pocket은 2025년 7월 종료, Omnivore도 종료. 로컬에 원문을 남기는 서재는 링크도 서비스도 사라져도 남는다
2. 쌓아두기만 하는 문제 해결: "안 보고 쌓아둔 기사·논문" 문제. 초록 카드로 훑고 필요한 것만 깊게 읽는 2층 구조가 효과를 낸다
3. 쓸수록 나를 닮는 분류: 몇 달 쓰면 칸 구성이 내 관심사 지도가 된다. 다른 도구는 처음 만든 폴더 구조에서 멈춘다

**5. 저작권과 공유 범위**

변호사가 아닌 입장에서 방향만 정리했다. 실제 공개·유료화 전에는 전문가 확인 필요.

기준은 "누가 저장해서 누가 보느냐". 원문을 숨기는지는 합법 여부를 가르는 기준이 아니다. 누가 쓰는지, 돈을 받는지, 원문을 대신하게 되는지가 기준

| 누가 저장 | 누가 봄 | 판단 방향 |
|---|---|---|
| 내가 | 나만 | 가능. 저작권법 제30조(사적이용 복제): 영리 목적이 아니고 개인적으로 이용 |
| 내가 | 친구 한두 명 | 유대관계가 깊은 소수라면 가능할 여지 |
| 내가 | 공개 GitHub, 블로그, 여러 명 있는 채팅방 | 한정된 범위를 벗어남 |
| 서비스가 | 돈 낸 사용자들 | 불확실하고 위험. 제30조는 개인 이용자 기준이라 영리 서비스 운영자에게 그대로 적용된다고 보기 어려움. 공정이용으로 다퉈야 하는 영역 |
| 서비스가 직접 긁어와서 | 요약을 팔아서 | 문체부·한국저작권위원회 2026.02 공정이용 안내서가 "뉴스 기사 전체를 크롤링해 요약 서비스를 자동 제공하는 행위"를 공정이용이 아닌 사례로 듦. 언론사 서비스와 목적이 같고 구독·광고 수익을 직접 훼손한다는 이유 |

정정 메모: 대화 중 "저장본은 담은 사람만 보게, 관련 기사는 발췌까지만"이라고 한 구조는 위험을 줄이는 방법이지 합법을 보장하는 구조가 아니다

친구 공유 기준 (찾기쉬운 생활법령정보, 제30조 해석)
- 허용 예시: 친구 한두 명에게 이메일로 전달, 유대관계가 깊은 소수 인원의 소규모 모임 안에서 이용
- 허용되지 않는 예시: 여러 사람이 볼 수 있는 온라인 카페·채팅방·블로그에 업로드, 유대관계 없는 카페 회원 전체에게 메일
- 핵심은 "폐쇄적이고 사적인 한정된 범위". 몇 명까지라는 숫자 기준은 법에 없음

| 공유 방식 | 판단 방향 |
|---|---|
| 책 한 권을 친구 한두 명에게 보내기 | 이메일 전달에 가까워 허용 여지가 큼 |
| 내 메모·요약 + 원문 링크만 공유 | 원문 복제본을 넘기지 않아 가장 가벼움 |
| 여러 친구가 같이 보는 공유 책장 | 채팅방 업로드에 가까워질 수 있어 조심 |
| 공개 링크로 누구나 보기 | 허용 범위를 벗어남 |

모든 기사가 보호받는 건 아니다
- 저작권법 제7조: "사실의 전달에 불과한 시사보도"는 보호 대상 제외
- 대법원 2006. 9. 14. 선고 2004도5350: 사건·사고, 기상 정보, 판결 내용처럼 정형적·간결하게 사실만 전하는 기사는 보호되지 않고, 그 수준을 넘어 개성 있는 표현이 담긴 기사는 보호
- AI·기술 기사는 해석과 분석이 많아 대부분 보호 대상일 가능성이 높다

기타
- 논문: arXiv 논문은 저자가 CC BY 같은 라이선스를 골라 올려서 라이선스마다 허용 범위가 다름
- 유료·로그인 기사: 저작권과 별개로 사이트 이용약관에 저장·복제 제한 조항이 있을 수 있음. 자주 담는 매체는 약관 확인
- 백업을 GitHub로 한다면 반드시 비공개 저장소. 공개 저장소는 사적 복제 범위를 벗어남
- (2026-09-23) 확장이 내가 보고 있는 화면의 본문을 저장하는 것도 복제에 해당한다. 개인 이용 범위 안에서는 같은 판단이 적용되고, 공개·유료화 시점에는 전문가 확인이 필요하다

유료로 간다면 설계 방향 (현재는 보류)
- 관련 기사는 요약 없이 제목·매체·날짜·링크 + "내 책장의 어느 글과 왜 관련 있는지" 한 줄 설명(서비스가 새로 만드는 내용)
- 요약을 판다면 언론사 API·제휴, 오픈액세스 논문처럼 라이선스 확인된 소스로 범위 좁히기
- 출시 전 저작권 전문가 확인

**6. 사용자가 나 하나인 것에 대해**

오히려 좋은 점
- 자기개선 루프가 깨끗하게 돈다. 신호 주는 사람이 하나라 기준이 섞이지 않는다. MultEval의 "사람끼리 기준 맞추기" 문제가 없다. EvalGen도 개발자 한 명의 판단에 평가자를 맞추는 구조
- 사용자 수 없이도 성과를 숫자로 보여줄 수 있다. 포트폴리오에서 보여줄 건 개선 과정
  - 자동 분류된 글을 다른 칸으로 옮긴 비율 (예: 1주차 40% → 8주차 12%, 숫자는 예시)
  - 요약을 다시 생성하거나 고친 비율의 변화
  - 프롬프트 버전별 같은 검증 세트 점수

한계
- 내 취향에만 맞춰져 다른 사람에게 통하는지 알 수 없음
- A/B 테스트나 퍼널 분석은 불가

나중에 넓힐 방법
- 각자 설치해서 쓰는 앱으로 공개: 서비스가 대신 저장하는 구조가 아니라 각 사용자가 자기 기기에서 자기 기사를 저장하는 도구로 배포. 방향으로는 훨씬 가볍지만 이것도 전문가 확인 필요. 확장은 각자 설치하는 형태라 이 구조에 가깝다
- Phase 앱 방향(로컬 마크다운 저장 + GitHub 동기화)과 이어진다 → 2026-09-23 해소: 마크다운으로 저장해 옵시디언과 공존하기로 하면서 같은 길이 됐다
- 친구 2~3명이 들어오면 "내 취향에만 맞춰짐" 한계가 조금 풀리고, 친구가 공유받은 글을 자기 책장에 담았는지 같은 신호도 생긴다

**7. 아카이빙: 기사·논문이 사라지는 걸 막는 법**

링크 소실: 퓨리서치센터 2024 조사. 2013년 웹페이지의 38%가 10년 뒤 접속 불가, 2013~2023년 존재 페이지 전체의 4분의 1이 사라짐

저장 형식 비교

| 형식 | 원문 모습 보존 | LLM 처리(요약·분류·검색) | 비고 |
|---|---|---|---|
| URL만 | 없음 | 매번 다시 가져와야 함 | 링크가 죽으면 끝 |
| PDF | 좋음 | 약함. 표·다단·각주에서 추출이 자주 깨짐 | 눈으로 보관하기 좋음 |
| HTML 스냅샷 | 좋음 | 보통. 광고·메뉴 섞여 정리 필요 | 용량 큼 |
| 본문 텍스트(마크다운) | 레이아웃 사라짐 | 가장 좋음 | 가볍고 검색 쉬움 |
| 웹 아카이브 링크 | 좋음 | 해당 없음 | Wayback Machine 등에 저장 요청 후 링크 보관 |

- PDF를 기본으로 두지 않는 이유: 참조표의 "요약에 원문에 없는 내용" 원인 후보가 파싱 실패. LLM이 읽을 텍스트는 처음 저장할 때 깨끗하게 뽑아두는 게 품질 관리에 유리
- DOI는 주소가 바뀌어도 찾아갈 수 있게 만든 영구 식별자

위험별 막는 방법

| 위험 | 막는 방법 |
|---|---|
| 원본 링크가 사라짐 | 담는 순간 바로 캡처. 본문 텍스트, 이미지, 메타데이터를 한 번에 |
| 원본이 조용히 수정됨 | 캡처 날짜 기록. "언제 본 버전인지" 남기기 |
| 로그인·유료 기사라 서버에서 못 가져옴 | 확장이 내가 보고 있는 화면의 본문을 대신 보냄 (2026-09-23 확정 경로) |
| 이미지·레이아웃 깨짐 | 마크다운과 함께, 이미지까지 한 파일에 담는 HTML 스냅샷을 선택 저장 |
| 외부에도 한 벌 | 저장할 때 Wayback Machine에 보관 요청, 받은 보관 주소를 메타데이터에 기록 |
| 논문 버전이 바뀜 | DOI·arXiv ID를 버전까지 저장 (예: 2404.12272v1). arXiv는 이전 버전 계속 보관 |
| 내 저장본이 망가지거나 없어짐 | 백업 3-2-1 원칙: 사본 3개, 매체 2종류, 1개는 다른 장소 |
| 파일이 몰래 손상됨 | 저장 시 파일 해시값 기록, 주기적으로 대조 |
| 앱이 없어짐 | 로컬에 일반 파일(마크다운, PDF)로 저장. 다른 프로그램으로도 열림 |
| 파일 형식이 낡음 | 오래가는 형식: 텍스트·마크다운, PDF/A(ISO 19005), WARC(ISO 28500) |

서재다운 기능
- 주기적으로 원본 링크 상태 확인 → 사라진 책에 "원본은 사라졌고 내 서재에만 남아 있어요" 표시. "사라지지 않는 서재" 메리트가 눈에 보이는 순간
- 담는 순간 깨끗한 텍스트를 받아두면 추천의 재료가 된다. 빌려주기, 아카이빙, 추천이 같은 저장 구조 위에서 이어짐
- (2026-09-23) 북마크 가져오기 결과 화면이 이 메리트를 보여주는 자리다. "가져온 북마크 중 몇 %가 이미 사라졌어요"

확장 단계(친구·다른 사용자)에서도 사라지지 않게: 원문 보관 책임을 서비스에서 떼어낸다

| 방법 | 누가 보관 | 한계 |
|---|---|---|
| 각자 기기에 저장 (로컬 우선) | 사용자 본인. 앱은 도구, 원문은 각자 기기나 각자 비공개 클라우드. 복제 주체가 개인이라 제30조 구조 유지 | 기기 백업은 사용자 몫 |
| 공개 아카이브에 맡기기 | Wayback Machine 같은 아카이브 기관. 서비스는 보관 주소만 저장 | 모든 사이트를 저장하진 않고, 영원히 보장되지도 않음 |
| 영구 식별자 활용 | 논문은 출판사와 arXiv. 학술 출판물은 CLOCKSS·Portico 같은 보존 시스템에 맡겨지기도 함 | 일반 기사는 영구 식별자가 거의 없음 |
| 허락된 소스만 보관 | 서비스. CC BY 같은 오픈액세스 논문·기사는 조건(출처 표시 등)을 지키면 저장·공유 가능 | 전체 중 일부만 해당 |

- 원문 대신 "내 것"을 보존: 메모, 하이라이트, 왜 담았는지, 다른 책과의 연결. 저작권법 제28조는 비평·연구 등을 위해 정당한 범위에서 공정한 관행에 맞게 인용하는 걸 허용. 서재의 가치는 원문보다 내 해석에 가깝다
- 확장 버전 구조
  - 원문: 각 사용자 기기나 저장소에 저장
  - 서버·공유에 올라가는 것: 메타데이터, 원본 링크, 아카이브 주소, 내 메모, 짧은 하이라이트
  - 원본이 사라지면: 내 사본이나 아카이브 주소로 자동 전환
- LOCKSS 원칙과 같은 구조: 스탠퍼드 도서관에서 시작한 디지털 보존 방식, "Lots of Copies Keep Stuff Safe"

**8. 사용 장면**

선택한 장면
1. 출근길에 링크드인에서 본 논문을 북마크했더니, 회사에서 컴퓨터를 켤 때 "LLM 평가" 칸에 꽂혀 있음 (2026-09-23 수정: 공유 버튼 → 북마크 + 크롬 동기화)
2. 주말에 새 탭을 열어보니 3주 동안 쌓인 글이 7개. 초록 카드로 훑고 2개만 깊게 읽음
4. 논문을 읽다가 모르는 용어를 그 책 안에 메모로 남겨둠
5. 몇 달 뒤 "평가" 칸이 너무 두꺼워서 "평가 기준"과 "평가 자동화"로 나눔
8. 책 한 권을 다 읽고 나니, 내 서재 안에서 같이 읽으면 좋은 책 두 권을 옆에 꺼내줌
추가. 저녁에 새 탭을 열면 "오늘 이 책은 어떠세요?" 큐레이션이 와 있음

선택하지 않은 장면 (후보로 보관)
3. 면접 전날 "LLM 평가" 칸을 통째로 꺼내서 요약과 내 메모로 복습함 → 칸 이어 읽기로 일부 살아남
6. 친구가 비슷한 고민을 하길래, 내 메모를 붙인 논문 한 권을 빌려줌
7. 반년 전에 담은 기사에 "원본은 사라졌고 내 서재에만 남아 있어요" 표시가 떠 있음

선택 장면의 흐름: 담기(1) → 소화하기(2, 저녁 큐레이션) → 기록하기(4) → 정리하기(5) → 연결하기(8)

장면별 기능

| 장면 | 필요한 기능 | LLM이 하는 일 | 쌓이는 신호 |
|---|---|---|---|
| 1. 북마크하면 알아서 꽂힘 | 북마크 생성 감지, 원문 캡처, 메타데이터 추출 | 주제 분류, 칸 배치 | 내가 다른 칸으로 옮김 |
| 2. 쌓인 글을 초록 카드로 훑음 | 안 읽은 책 모아보기, 초록 카드, 깊게 읽기 전환 | 초록 카드 생성(기사는 핵심 요약) | 카드만 보고 넘김 / 깊게 읽기로 들어감 |
| 4. 모르는 용어를 책 안에 메모 | 본문 하이라이트, 메모, 용어 설명 | 용어 설명 초안 제안 | 제안을 그대로 둠 / 고침 / 지움 |
| 5. 두꺼운 칸을 둘로 나눔 | 칸 나누기·합치기, 책 일괄 이동 | 칸이 두꺼워지면 나누는 방법 제안 | 제안 수락 / 직접 다르게 나눔 |
| 8. 다 읽으면 같이 읽을 책을 꺼내줌 | 읽음 표시, 관련 책 추천 | 본문끼리 비교해 비슷한 책 찾기 | 추천을 열어봄 / 무시함 |
| 추가. 저녁 "오늘 이 책은 어떠세요?" | 새 탭에 뜨는 카드 또는 크롬 알림 | 오늘의 책 고르기, 추천 이유 한 줄 | 열어봄 / 넘김 / "이런 건 그만" |

- 5번은 criteria drift가 앱 안에서 일어나는 장면. 칸이 30권쯤 쌓이면 "이 칸을 이렇게 나눠볼까요?" 하고 LLM이 제안하고 내가 받아들이거나 고치는 mixed-initiative 방식

**9. 저녁 큐레이션 설계**

기준 후보 (여러 개를 섞기로 함)
- 담아두고 한 번도 안 연 책 중 오래된 것
- 오늘 담은 책과 연결되는 예전 책
- 요즘 자주 여는 칸의 책
- 한동안 안 연 칸의 책 (잊고 있던 관심사 다시 꺼내기)
- 카드만 보고 넘겼던 책 중 지금 관심사와 가까워진 것
- (요일마다 기준을 바꾸는 방식도 가능)

전달 방식: 저녁에 새 탭을 열면 사서 자리에 카드, 또는 정해진 시간에 크롬 알림 (2026-09-23 수정: PWA 알림 → 크롬 알림)

알고리즘은 사용자에게 숨긴다
- 이유를 모르고 받는 책이 더 설렌다. 도서관에서 찾던 책 옆 책을 우연히 발견하는 경험. 문헌정보학에서도 우연한 발견(serendipity)을 정보 탐색의 한 유형으로 연구
- 단 사용자에게는 숨기되 기록에는 남긴다. 카드마다 어떤 기준으로 뽑혔는지 로그에 있어야 자기개선 루프가 돈다

섞는 방식: 비중을 조절하는 추첨 (멀티암드 밴딧)
- 처음엔 모든 기준을 비슷한 비중으로
- 열어본 카드의 기준은 비중이 조금씩 오르고, 넘긴 카드의 기준은 내려감
- 일정 비율은 항상 낯선 기준에 남겨둠. 열어본 것만 따라가면 늘 비슷한 책만 오고 우연한 발견이 사라짐

흥미 유지 장치
- 같은 책이 연달아 오지 않게, 넘긴 책은 일정 기간 후보에서 제외
- 내 서재 안의 책만 오니까 너무 엉뚱하진 않음
- "이런 건 그만"을 누르면 그 기준 비중을 크게 낮춤

평가
- 기준별 열어본 비율, "이런 건 그만" 비율
- 열어본 비율만 올리면 안전한 책만 오게 되므로, 낯선 기준에서 온 책을 열어본 경우를 따로 세어 우연한 발견이 살아 있는지 확인

이유 공개 방식: **열어본 뒤 공개로 확정** (다른 후보였던 것: 끝까지 비밀, 힌트만)

기준별 공개 문구 예시

| 뽑힌 기준 | 열어본 뒤 나오는 이유 |
|---|---|
| 담아두고 안 연 오래된 책 | "3주 전 출근길에 담아두고 잊고 계셨던 책이에요" |
| 오늘 담은 책과 연결 | "오늘 담으신 ○○와 같은 질문을 다룬 예전 책이에요" |
| 요즘 자주 여는 칸 | "요즘 자주 찾으시는 'LLM 평가' 칸의 책이에요" |
| 한동안 안 연 칸 | "두 달 동안 펼치지 않은 '추천 시스템' 칸에서 꺼내왔어요" |
| 카드만 보고 넘긴 책 | "지난번엔 카드만 보고 지나치셨는데, 요즘 관심사와 가까워졌어요" |

품질 관리
- 이유 문구 속 사실값("3주 전", "출근길", "두 달")을 LLM이 지어내면 안 됨
- 기준과 사실값: 로그와 DB에서 코드로 가져옴 (결정론적)
- 문장 다듬기: LLM이 자연스러운 말투로 (확률적)
- "이유 문구 속 사실이 실제 기록과 맞는가"를 코드로 바로 검사

공개 순간의 신호
- 이유를 보여준 직후 "이런 이유라면 좋아요" / "이건 별로" 반응 받기
- 책을 열었는지보다 어떤 이유가 마음에 들었는지를 직접 알려줘서 기준별 비중 조절에 더 정확한 재료

**10. LLM 지점·평가·신호 (기능 단위)**

| 기능 | LLM이 하는 일 | 평가 기준 | 사용하며 생기는 신호 |
|---|---|---|---|
| 담기 | 제목·저자·날짜·출처 추출 | 정확한가 (코드 체크) | 메타데이터를 고침 |
| 책장 배치 | 주제 분류, 칸 결정 | 주제가 맞나, 너무 넓거나 좁지 않나 | 다른 칸으로 옮김, 새 칸 생성 |
| 요약 | 핵심 요약 | 원문과 일치하나, 핵심 누락 없나 | 다시 생성, 직접 수정, 원문 열어봄 |
| 관련 기사·책 | 관련 항목 검색·정렬 | 관련 있나, 최신인가, 중복 없나 | 클릭, 책장에 담음(가장 강한 신호), 숨김 |

- 이 신호들이 iML의 "라벨 → 모델 개선" 통로를 되살린다. 따로 채점하지 않아도 내가 고친 기록이 실패 이유가 되고, 모으면 반성 단계에 넣을 재료가 된다. 취향이 바뀌면 수정 패턴도 바뀌어 criteria drift를 자연스럽게 따라간다
- 자기개선 루프는 책장 배치부터 붙이는 게 좋다. 신호가 가장 많고 명확하다
- 요약·관련 항목은 품질이 곧 신뢰. 자동으로 프롬프트를 바꾸기 전 검증 단계를 꼭 거친다
- 관련 기사 정렬: 관련성 기준 통과 → 최신순의 두 단계
- 요약 신뢰: 요약 문장마다 원문 위치를 연결하면 바로 확인 가능, 환각도 드러남
- 비용: 요약은 담을 때 한 번 만들어 저장, 관련 기사는 주기적으로 갱신

책장 메타포가 평가 단위를 정해준다
- 책 한 권: 메타데이터, 요약 품질
- 칸 하나: 같은 주제끼리 잘 모였나
- 책장 전체: 주제 구조가 한눈에 들어오나

**11. 증상-원인-확인법 참조표 (서재앱 버전)**

결정론적 실패(매번 같게 틀림 → 규칙·구조 수정)와 확률적 실패(돌릴 때마다 다르게 틀림 → 프롬프트·반복 검증)를 구분

| 증상 | 원인 후보 | 확인법 |
|---|---|---|
| 논문이 엉뚱한 칸에 꽂힘 | 매번 같은 칸이면 칸 정의가 모호함(결정론적) / 돌릴 때마다 다르면 경계에 걸친 주제(확률적) | 같은 글을 3~5회 분류해서 결과가 같은지 |
| 요약에 원문에 없는 내용이 들어감 | 초록만 들어가서 나머지를 추론으로 채움 / 전문 파싱 실패 | 요약 문장마다 원문 근거 대조, LLM 입력 길이 확인 |
| 관련 기사가 최신순인데 오래된 게 위에 옴 | 날짜 추출 실패 또는 정렬 로직 오류(결정론적) | 기사별 날짜 필드 값 확인 |
| 하루 걸러 수집이 안 됨 | 스케줄러·권한·API 제한 같은 인프라 문제(결정론적) | 실행 로그에서 실패 시점과 에러 메시지 |
| 본문이 깨져 보임 | 경로별 파싱 실패(결정론적) | 같은 매체 글 3건을 같은 경로로 다시 돌려 재현되는지 |
| 하이라이트가 사라짐 | 원문이 수정되어 문장을 못 찾음 | 저장된 인용문과 현재 페이지 대조 |
| (큐레이션) 이유 문구의 사실이 틀림 | LLM이 사실값을 지어냄 | 문구 속 사실값을 로그·DB와 코드로 대조 |

- 네 번째 줄이 Hermes에서 겪은 문제. 결정론적 실패라 프롬프트로는 고칠 수 없고, 자기개선 루프에 넣기 전에 구조부터 잡아야 한다
- 첫 줄의 두 원인은 책장 구조에서 처리 경로가 정해짐: 결정론적은 규칙 질문 → 범위주기 수정, 확률적은 참조 카드·임시서가 (`서재앱_책장구조_260922.md` 7번)

**12. 다른 대화의 기존 요약과 비교 (붙여주신 내용 기준)**

기존 요약 내용
- 개인 서재 PWA: 기존 Hermes 파이프라인을 확장해 "안 보고 쌓아둔 기사·논문·영상을 저녁에 요약해주는 개인 아카이브"
- 논문은 초록 기반 가벼운 카드 + 전문 분석 깊은 필드의 2층 구조
- 분류 체계는 문헌정보학 전공을 살려 도서관 분류 체계 기반
- Phase 0~9 실행 순서, 설계 7축 점검표(가치·UX·데이터·로직·인프라·신뢰·성장) 체크리스트 산출물
- LLM-as-Judge, Agent-as-a-Judge를 기획 파트에서 활용하는 접근 탐색
- Hermes: Collector → Analyzer → Writer, SQLite, ChromaDB(RAG), 텔레그램

비교

| 항목 | 기존 요약 | 이후 결정 | 상태 |
|---|---|---|---|
| 기반 | Hermes 확장 | Hermes 교체 예정 | 교체로 정리됨 |
| 형태 | 개인 서재 PWA | 크롬 확장 (2026-09-23) | 폰 PWA는 다음 단계 |
| 담는 대상 | 기사·논문·영상 | 논문·기사 위주 | **영상 포함 여부 미정** |
| 요약 방식 | 저녁에 요약해서 보내주기 | 개인 기능으로, 저녁 큐레이션 추가 | 저녁 요약과 저녁 큐레이션의 관계 정리 필요 |
| 사용자 | 개인 아카이브 | 개인 + 친구 한두 명 공유 | 공유는 셋째 단계 |
| 고도화 방향 | 없음 | 자기개선 루프 | 7축 중 "성장"에 배치 제안 |

보완 제안
1. 분류 체계는 원리만: KDC·DDC를 그대로 쓰면 AI 논문·기사가 거의 한 칸에 몰림. 계층 구조, 통제 어휘 원리를 가져오고 칸은 관심 분야에 맞게 세분. 패싯 분류도 책장 UI와 맞음
2. 2층 구조 활용: 초록 카드는 기본, 전문 분석은 깊게 읽기로
3. 7축 배치: 평가 기준과 요약 원문 근거 표시는 "신뢰" 축, 사용 신호로 분류·요약이 나아지는 루프는 "성장" 축

오래된 정보
- AVIKO 평가 프레임워크 "구축 진행 중" → 9월 29일 마지막 근무일로 곧 종료
- Hermes 파이프라인은 중단된 상태

기존 요약의 협업 원칙 (함께 옮겨온 내용)
- 발산 후 수렴: 아이디어를 먼저 늘어놓고 탐색이 무르익은 뒤 수렴·검증
- 흥미를 잃는 타이밍의 검증 요청은 불편. 흐름에 맞는 개입 타이밍
- 추상적 설명보다 구체적 예시와 실행 가능한 체크리스트
- 근거 없는 단정에 민감, 즉각 수정과 실제 근거 확인 기대
- 결정론적 실패 vs 확률적 실패 구분이 AI 품질 진단의 핵심 축
- 증상-원인-확인법 3열 참조표를 꾸준히 축적하는 것이 진단 역량 자산화 방법
